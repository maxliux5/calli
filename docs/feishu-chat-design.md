# 飞书对话：专用机器人，不添加提示词

2026-11-10 · 设计稿，实现中。属于 TODO 第 5 节「通知与手机」，与[推送](push-design.md)共用 Lark CLI 的传输方式，但使用独立机器人。

在飞书里私聊 Calli，开始一个线程；一轮结束，机器人把最终回答回复到对应消息。回复某条机器人消息，就接着那个线程聊。电脑上的 Calli 仍然能查看、继续和审批同一线程。

## 目标与边界

- 飞书是另一个人的输入入口。文本成为普通用户消息，不加入来源说明、机器人身份、回复格式、协议标签或飞书专用提示；agent 不需要知道这是飞书。这里的「零注入」指不添加内容：与网页发送一样，`startTurnReady` 去掉首尾空白，中间换行和缩进保留。
- 一次独立来信对应一个新线程；显式回复或引用已经关联的消息才续线程，避免把无关事情混在一起。
- 复用 Calli 的线程、队列、权限和生命周期，不启动第二套 agent 管理器，不改 agent 的配置和会话。
- 只接专用机器人的私聊、只认一个主人。默认关闭，由人选择 agent 和工作目录后启用。

首版不做群聊、多人授权、图片和附件输入、流式卡片、飞书内审批、自动读取聊天历史、多机器路由，以及重启后补跑尚未完成的飞书任务。不因为飞书来信而放宽 agent 的已有权限。

## 参考与取舍

参考 BotMux 的[零注入说明](https://github.com/deepcoldy/botmux/blob/master/docs/zero-prompt-injection.md)、按话题隔离会话和 [`registerApp` 设备授权流程](https://github.com/deepcoldy/botmux/blob/master/src/setup/register-app.ts)；传输直接使用 [Lark CLI](https://github.com/larksuite/cli)。Calli 已经管理多个 agent 和线程，再接 BotMux 会多出一套会话归属、进程生命周期与权限入口，所以借鉴交互和隔离原则，不把它作为运行依赖。

mew 是内部闭源 CLI（npm 包 `@byted-codebase/mew`）。以下依据本机 `mew lark --help` 及子命令帮助，未读其源码；只比较可见命令能力，不据此推断内部调度、存储或恢复保证。

| 关注点 | mew 命令帮助可见能力 | Calli 首版取舍 |
|---|---|---|
| 何时触发、交给谁 | `bind-chat` 的 `trigger-policy` 有 `mention / all / topic_starter_and_mentions`，并指定 `default-agent-id` | 只接受主人直接私聊，使用设置里的 agent；不根据关键词或模型判断发起工作 |
| 回复方式 | `bind-chat` 的 `reply-policy` 有 `thread / direct` | 回答回复来信；用户回复已关联消息才续 Calli 线程 |
| 收件账本 | `list-ingress-events` 可按消息 ID、状态、原因等查入站事件 | 私聊入站记录接收或拒绝原因，用 `message_id` 去重；群聊和非用户事件不记账 |
| 发件账本与重试 | `list-deliveries` 独立列投递，`retry-delivery` 可重排指定投递 | 回答单独记录并带稳定幂等键，失败自动重试两次 |
| 按需上下文 | `read-context` 可按事件、轮次或快照查当前及历史上下文 | 借鉴 agent 自己按需读取的入口思路，不在飞书用户消息中塞上下文；首版不接历史读取 |
| 连接方式与诊断 | `update-workspace-bot` 的 `transport-mode` 有 `callback / long_connection / auto`，另有 `test-connection` | 仅用 Lark CLI 长连接，保留连接状态与测试发送 |

取舍是把触发、收件记录、发件记录和重试分开。mew 帮助未说明的持久化与恢复细节不作结论；Calli 首版明确只有入站去重与消息映射持久化，待回复、重试和最近记录在内存中。

## 一条消息的流转

1. daemon 启用飞书对话后，用 `lark-cli --profile calli event consume im.message.receive_v1 --as bot --dry-run` 检查事件订阅与凭证。
2. 预检通过后以同样 profile 建立长连接，逐行读取 NDJSON。诊断文字与消息正文分开处理，坏行不进入 agent。
3. 解析私聊、真实用户发送的文本；群聊和非用户事件直接忽略，不计入记录。原始飞书事件的文本 JSON 正文先取出 `text`；平铺事件已渲染的文字保持原样，即使文字本身也是带 `text` 字段的 JSON。
4. 以 `message_id` 认领来信。重复投递不重复启动线程或轮次；去重标记存 SQLite，保留七天。
5. 检查主人。未绑定时只记录 `pendingOwner` 和 `owner_missing`，不执行、不自动认领第一个来信者；其他人的消息记录拒绝原因。
6. 根据回复目标查线程；没有可用映射就新建线程。标题可以压缩为短摘要，正文沿用网页相同的首尾空白处理，不追加任何提示词。空白或超过 8,000 字符的文本拒绝处理，不静默截成短消息。
7. 记录来信与线程的对应关系，给来信加一个处理中反应，将原文送入 `ThreadManager.startTurn`。线程忙时沿用队列，每条来信保留自己的回答目标；正在执行的网页轮次不能拿走后来的飞书回答。
8. 监听当前轮次的结束或等待事件。正常结束取最终文字，失败或主动停止发简短说明；审批或输入请求只提示回 Calli 处理。
9. 通过 `im +messages-reply` 回复对应来信。正文走标准输入，命令走参数数组；同一回答的每次重试使用相同幂等键。
10. 成功返回的机器人 `message_id` 也关联到线程，供下次回复续接；发件记录更新为已发或失败。

## 线程与飞书消息的对应

| 飞书动作 | Calli 行为 |
|---|---|
| 直接发一条文本，没有回复目标 | 新建线程 |
| 回复或引用已知机器人消息 | 进入该消息关联的线程 |
| 回复已经关联的用户来信 | 同样续进关联线程，可在回答尚未到达时排队 |
| 回复的消息没有映射，或对应线程已删除 | 新建线程 |
| 同一 `message_id` 再次投递 | 忽略，不再启动轮次 |
| 在网页继续飞书来源的线程 | 默认只在网页回答；开启 `echoWeb` 后也回传飞书 |
| 网页中没有飞书映射的普通线程 | 不通过此机器人发送 |

映射只凭消息 ID，不能从正文里的线程名、链接或“继续上次”猜测。回复映射包含机器人消息与用户来信，不能只保存最后一个线程。

## 权限与安全

- `owner` 是唯一允许发起工作的飞书 `open_id`。未绑定时的 `pendingOwner` 只是候选，设置页要提醒人核实，再显式保存；不会因为收到一条消息就自动绑定。
- 扫码创建完成后，如果 Lark CLI 明确提供已授权用户的 `openId`，且当前尚未设置主人，可以用这个身份初始化 `owner`。已经设置的主人不被覆盖；无法取得身份时保留未绑定状态。
- 独立 profile 名固定为 `calli`，避免与个人助手的飞书连接或其他工具共用应用、争抢同一个事件连接。创建应用使用 `lark-cli config init --new --name calli`，此时 profile 尚不存在，不加全局 `--profile`；其他调用均带 `--profile calli`。已有应用时返回 409，避免覆盖。
- 飞书凭证归 Lark CLI 管理。Calli 只读取身份状态，不保存 app secret、访问 token 或用户凭证，不把 CLI 的原始 stderr 或进程错误直接展示给网页。
- 启动 CLI 前清除全部 `CALLI_*` 环境变量，包括 hub、协作和工具凭证；不经 shell 执行，消息正文不拼入命令参数。
- 飞书设置接口沿用 hub 鉴权。消息中的深链不携带 token；只有设置了 Calli 地址才附上链接。
- agent 的最终文字会发给飞书，等于离开本机。不会额外回传思考过程、工具原始输出、完整审批命令或其他线程历史。失败说明可能带有限的错误摘要；回答本身如果包含敏感信息，仍属于回传范围。
- 等待批准时只说「等你批准」，同一轮只通知一次，审批继续在 Calli 完成。飞书文字不能直接替代审批操作。

## 状态机

`configured` 只说明 CLI 的专用应用已存在；`botReady` 说明机器人身份可用；`realtime` 表示收件连接。三者分开，不能把“应用已建好”当成“已经能收消息”。

| `realtime` | 含义 | 处理 |
|---|---|---|
| `off` | 对话开关关闭 | 不保持事件连接 |
| `connecting` | 正在预检或建立连接 | 保留已有设置与记录，显示连接进度 |
| `live` | 连接已就绪，能够接收事件 | 正常处理来信 |
| `console-off` | 开发者后台的事件订阅未发布或未启用 | 明确提示检查后台；降低重试频率 |
| `busy-elsewhere` | 同一应用已有其他事件连接 | 提示连接冲突，检查是否用了专用机器人；降低重试频率 |
| `unavailable` | CLI 缺失或凭证不可用 | 显示安装、身份或应用状态；降低重试频率 |
| `error` | 其他启动、预检或连接失败 | 记录概况，退避重连 |

普通断连采用退避，最长五分钟；配置性问题采用较慢重试。关闭开关或 `dispose()` 会停止消费者、取消重连；销毁同时终止扫码和正在执行的 CLI 子进程。

扫码状态独立为 `idle → waiting → done / failed`。`waiting` 给出 CLI 输出的 HTTPS 授权链接；取消返回 `idle` 并结束进程。成功后清掉链接并刷新身份；失败或超时不把 CLI 原始日志暴露给页面。扫码、保存设置与消息处理不能互相覆盖主人身份。

## 记录、重试与加载

- 入站记 `received / failed / dropped`，出站记 `sent / failed`，携带方向、时间、消息或回答键、线程、标题和简短原因。
- 最近最多 20 条记录和丢弃计数保存在内存。SQLite 保存入站去重和消息映射；进程重启后不会从最近记录重放执行。
- 每次发送默认最多 15 秒，首次失败后最多重试两次，间隔递增。幂等键从回答身份稳定生成，不能在重试时重新随机。
- 最终回答最多回传 20,000 字符，超出后保留开头并明确标注截断；配置了 Calli 地址时给出全文线程链接。不能先被其他摘要函数静默截去前文。
- 状态概况使用 `?summary=true`，只带最近一条记录；展开详情才取完整最近记录。配置性错误、未绑定身份和当前连接失败仍直接可见。
- 当前原因枚举包含 `cli_missing`、`bot_not_ready`、`timeout`、`owner_missing`、`cli_failed`、`not_owner`、`unsupported`、`rate_limit`、`console_off`；展示未知原因时要有明确失败回退，不能当正常或空数据。

## 接口

所有接口均需 hub 身份验证，JSON 正文。

| 方法与路径 | 输入或返回 | 约定 |
|---|---|---|
| `GET /api/feishu/settings` | `{enabled, agent, cwd, owner, echoWeb}` | 默认关闭，`owner` 可空 |
| `PUT /api/feishu/settings` | 同上，允许局部更新 | 校验布尔类型、已知 agent、绝对目录和 `ou_` 身份；启用前需 agent 与目录 |
| `GET /api/feishu/status` | `{cli, configured, botReady, reason, realtime, setup, pendingOwner, records, dropped}` | 完整最近记录；`setup` 为 `{state, url, reason}` |
| `GET /api/feishu/status?summary=true` | 同上 | 最近记录最多一条 |
| `POST /api/feishu/setup` | 返回当前状态 | 发起扫码；重复发起复用当前进程，已配置返回 409 |
| `DELETE /api/feishu/setup` | 返回当前状态 | 取消正在等待的扫码 |
| `POST /api/feishu/test` | 202，返回发件记录 | 通过专用机器人给主人发送连通测试；未绑定记 `owner_missing` |

## 已知限制

- 混合网页与飞书同时排队时，不能只凭先后次序推断回答归属。当前通过轮次开始时的文本匹配绑定来信，已覆盖网页正在运行、飞书随后排队的场景；若多个来源排队且内容相同，仍可能匹配错位。使用稳定的来信标识贯穿轮次队列后，才能消除这类歧义。
- 待回复和重试不跨 daemon 重启恢复；收件去重持久化意味着重投同一消息也不会自动重跑。重启中断后需由人查看线程并重新发起。
